¿Cómo interpreto este número?

Un índice mayor indica más señales históricas de cancelación. No es una probabilidad calibrada: 40/100 no significa exactamente un 40 % de probabilidad. La decisión sigue siendo humana.

Tus datos · guardado local

Mis reservas

Las reservas se conservan al recargar la página o reiniciar la aplicación. Cada computador tiene su propia copia; no se sincronizan entre compañeros.

Pulsa una tarjeta para ver sus registros. Guardadas incluye todos los estados; al elegir una tarjeta se limpia la búsqueda.

Reservas activas

“Revisada” solo registra que tú examinaste los datos. No significa que el huésped confirmó, canceló o fue contactado. Archivar oculta la reserva de las activas; puedes restaurarla.

El guardado vive en la carpeta .runtime del proyecto. Conserva esa carpeta al moverlo a otro lugar. La copia descargada es un archivo JSON para consulta y respaldo de los datos; esta versión no tiene importación de copias JSON.

Tu primera reserva · con calendario

De las fechas a una reserva guardada

  1. Fechas: entra en Nueva reserva. Selecciona la llegada y después la salida. La última fecha es el día en que sales: no añade otra noche.
  2. Detalles: continúa, añade una referencia y revisa las seis opciones del hotel y la reserva. Cada campo explica qué significa.
  3. Revisar y guardar: comprueba el resumen y pulsa Analizar y guardar. Espera el mensaje con código RI-… y abre Mis reservas.

Prueba concreta: en “¿La reserva se creó otro día?” escribe 01/10/2026; elige llegada el 02/10 y salida el 05/10. Debe mostrar 3 noches: 1 entre semana y 2 de fin de semana, con 1 día de anticipación. Es un caso de práctica, sin desenlace conocido.

Hoy se usa como fecha de creación al empezar. Puedes elegir llegadas hasta 60 días después y estancias de 1 a 30 noches. El calendario registra fechas; no consulta habitaciones disponibles ni confirma una compra.

    Arquitectura de la solución

    Componentes de Azure ML

    Las flechas muestran datos y artefactos. El pipeline contiene tres etapas; registro y descarga son pasos posteriores. La demo usa el modelo verificado y las métricas descargadas, sin endpoint permanente. Las nuevas reservas y su resultado se guardan en SQLite en el computador del usuario; no se incorporan al entrenamiento ni alteran la evidencia histórica.

    Leer el flujo paso a paso
    1. Datos y preparación: Blob conserva el CSV. Preparación aplica el alcance, retira duplicados y separa entrenamiento, validación y prueba por fechas.
    2. Entrenamiento: compara candidatos, elige el modelo y fija el umbral utilizando validación.
    3. Evaluación: recibe el modelo fijado y la prueba reservada; produce métricas y predicciones. No vuelve a entrenar.
    4. Registro y descarga: se versiona el modelo y se verifican su huella y sus resultados antes de usar la copia local.
    5. Uso local: calendario o CSV → validación → inferencia → guardado opcional en SQLite → revisión humana. Mis reservas consulta esa base.

    Workspace organiza trabajos y versiones; el clúster CPU ejecuta las tres etapas con 0–1 nodos. El entrenamiento de Azure es histórico y su grupo temporal fue cerrado. La demo funciona con los artefactos descargados.
